# Application tracking and privacy

Application lifecycle status is independent of résumé readiness. `/applications/{id}/tracking` supports optimistic revision checks, lifecycle updates, notes, next actions, and timezone-qualified follow-up dates. Events are append-only; follow-up dates are stored, not automatic reminders. A first `submitted` status requires current valid approval and freezes the exact job description/requirements, artifact version/hash/claims, and evidence. Later edits cannot rewrite that historical submission snapshot. This records candidate-reported submission, not proof that an employer received it.

`/account/audit` exposes up to 500 most recent owner-scoped operation records. It records route templates, action, response status and time, never bodies, query strings, cookies, passwords or API keys. Account exports include the full audit history. This is an application audit trail, not tamper-proof infrastructure logging.

`GET /account/export` streams a ZIP response (currently assembled in memory) containing JSON records, original uploaded source documents and stored résumé export files. Password hashes, sessions, worker lease tokens, broker dispatch data and internal storage keys are excluded. Missing source files fail the whole export rather than silently claiming completeness. Large-account streaming/background export is a production follow-up.

`POST /account/delete` requires the exact confirmation `DELETE MY ACCOUNT`, revokes all sessions and blocks sign-in immediately. A transactional outbox schedules cleanup via Celery. Cleanup discovers owned data through the relational ownership/foreign-key graph, deletes it in dependency order, and persists a minimal storage-key manifest while private file deletion is pending. File cleanup retries after failure or interruption. Once complete, the manifest and owner identifier are erased; only a non-identifying job receipt/status remains. Retry recovery backs off from one minute to one hour and deduplicates pending dispatch. Workers refuse to commit results for accounts pending deletion or already removed.

This covers this application's database and private local storage. There is no configured backup/cloud storage/provider deletion integration or production retention contract; those must be verified before real candidate data. No third-party model request history is deleted by this local cleanup. User data already downloaded by the candidate cannot be recalled. Production use remains disabled by the existing application guard.

PostgreSQL integration exposed and fixed an audit transaction self-deadlock: an idempotent response could retain an owner-row lock until request cleanup while an independent audit transaction waited for that same row. Audit now rolls back the request's residual read/error transaction and records metadata in that session after explicit endpoint commits. A regression asserts that an error after an uncommitted write does not persist that write; duplicate-response audit is covered on PostgreSQL.
